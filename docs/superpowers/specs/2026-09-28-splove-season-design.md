Дата: 2026-09-28. Статус: согласован с Виктором. Срок: к 1 октября 2026, когда стартует сезон «Осень».

Идёт **раньше** описания `2026-09-28-splove-stages-design.md` (ступени, пасхалки, препятствия), которое ждёт своей очереди. День сплава, бустеры и посты бота в чат вынесены в шаг 2.

## Зачем

Игра держится на десятках игроков из закрытого чата. Нужны повод возвращаться, цель на всё лето и цифры, по которым продюсер видит, работает ли это. Сезонные баллы дают всем шанс (в отличие от очков за мастерство), задания создают недельный ритм, `/metrics` показывает, что происходит.

## Договорённости

- Сезоны: **Осень** 1 окт – 31 дек, **Зима** 1 янв – 31 мар, **Весна** 1 апр – 30 июн, **Лето** 1 июл – 30 сен. Всё по Москве (UTC+3), границы включают первый день и не включают день после последнего. Даты хранятся в таблице, их можно менять.
- Баллы копятся **весь год**, сезоны дают только титул «чемпион сезона» и значок, без денег. Скидки на сплаве в конце лета по общей сумме: 1-е место 15%, 2-е 10%, 3-е 5%. Победителю ещё индивидуальная скидка и приз (определится позже). Проверка победителей руками до выдачи.
- Неделя считается с понедельника 00:00 по Москве. Ключ недели — ISO-неделя московской даты (`2026-W40`). 1 октября 2026 попадает в неполную неделю W40, с 28 декабря 2026 по 3 января 2027 идёт W53.
- **Источник времени** для прогресса заданий, дней игры (`days3`) и проверки «сезон идёт» — серверное `runs.created_at`, переведённое в МСК. Клиентский `started_at` не используется: он может отставать на 30 дней и открывал бы накрутку старых недель.
- Игровые очки (рекорды, таблицы по сложностям) и сезонные баллы — разные числа и разные таблицы.
- Никаких сообщений бота в чат в этом шаге.

## Данные

Миграция `worker/migrations/0006_season.sql`:

```sql
CREATE TABLE seasons (
  id TEXT PRIMARY KEY, title TEXT NOT NULL,
  starts_at INTEGER NOT NULL, ends_at INTEGER NOT NULL      -- секунды UTC
);
INSERT INTO seasons VALUES
 ('autumn-2026','Осень',1790802000,1798750800),

 ('spring-2027','Весна',1806526800,1814389200),

CREATE TABLE visits (
  tg_id INTEGER NOT NULL,
  day   TEXT    NOT NULL,                                   -- YYYY-MM-DD по Москве
  PRIMARY KEY (tg_id, day)
);
CREATE INDEX idx_visits_day ON visits (day);

-- Историю визитов до сезона восстанавливаем из игроков и заплывов:
-- иначе все действующие игроки выглядели бы новичками в день выкладки.
INSERT OR IGNORE INTO visits (tg_id, day)
  SELECT tg_id, date(created_at,       'unixepoch', '+3 hours') FROM players;
INSERT OR IGNORE INTO visits (tg_id, day)
  SELECT tg_id, date(created_at,       'unixepoch', '+3 hours') FROM runs;

CREATE TABLE points (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  tg_id INTEGER NOT NULL,
  season_id TEXT NOT NULL,
  key TEXT NOT NULL,                                        -- q:autumn-2026:2026-W40:gena
  points INTEGER NOT NULL, at INTEGER NOT NULL,
  UNIQUE (tg_id, key)
);

ALTER TABLE runs ADD COLUMN gena    INTEGER NOT NULL DEFAULT 0;
ALTER TABLE runs ADD COLUMN bottles INTEGER NOT NULL DEFAULT 0;
ALTER TABLE runs ADD COLUMN camps   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE players ADD COLUMN banned INTEGER NOT NULL DEFAULT 0;
```

Уникальный ключ `(tg_id, key)` делает начисление идемпотентным: повторная отправка заплыва не даст баллов дважды.

У `visits` и `points` нет внешних ключей на `players`: D1 их проверяет, и шесть существующих тестов, которые делают `DELETE FROM players`, начали бы падать. Целостность держит `authorize`, который создаёт игрока раньше записи. Миграцию 0006 применяем на боевой базе **до** выкладки воркера.

## Что считает клиент

К телу заплыва добавляется необязательное `stats: { gena, bottles, camps }`: сколько раз подобран Гена, сколько бутылок, сколько лагерей пройдено. Счётчики ведёт игра в `collect()` и в обработчике лагеря, в отдельном объекте `G.st = { gena, bottles, camps }` (поле `G.gena` уже занято таймером Гены на 22 секунды).

**Возврат в лагерь.** `continueRun` откатывает лодку к последнему лагерю и заново рассыпает бутылки, поэтому без защиты их посчитали бы дважды. При прохождении лагеря делается снимок `G.stSnap = { gena, bottles }`, а `continueRun` возвращает счётчики к снимку. Счётчик лагерей не откатывается: лагеря до `lastCamp` пройдены.

Сервер проверяет правдоподобие: `bottles <= meters/27 + 2`, `gena <= meters/1000 + 1`, `camps <= (meters >= 400 ? floor((meters-400)/500) + 1 : 0)`, всё целые и неотрицательные. Не прошло — статистика обнуляется, сам заплыв засчитывается как обычно.

## Задания

- Общий набор в `worker/src/season/quests.ts`. Номер недели `weekIndex` = число недель от фиксированного понедельника 2026-09-28 (по Москве). Берутся три подряд идущих задания набора по кругу, начиная с `weekIndex % 5`. У всех игроков одни и те же. «Подобрать Гену» — сумма за все заплывы недели не меньше 1.
- Начальный набор:

| id | Задание | Цель | Баллы |
|---|---|---|---|
| gena | Подобрать Гену | Гена ≥ 1 | 150 |
| camp3 | Дойти до 3-го лагеря | camps ≥ 3 в одном заплыве | 200 |
| bottles10 | Собрать 10 бутылок | сумма за неделю ≥ 10 | 100 |
| km2 | Проплыть 2 км | сумма метров за неделю ≥ 2000 | 150 |
| days3 | Сыграть в 3 разных дня | 3 дня с заплывом | 200 |

- «Выпей с Санчезом» и «финиш» добавятся в набор, когда появятся Санчез и финиш.
- После каждого принятого заплыва (`rejected IS NULL`) считается прогресс недели по таблице `runs` и, если задание выполнено, добавляется строка `points` с ключом `q:<сезон>:<неделя>:<id>` (`INSERT OR IGNORE`). Максимум за неделю ограничен суммой трёх заданий.
- Начисление вызывается и на пути «заплыв уже записан» (повтор из офлайн-очереди): если первый запрос оборвался между записью заплыва и начислением, баллы не пропадут.
- Ответ `/api/runs` получает поле `newQuests` со списком только что выполненных заданий, игра показывает их в тексте результата.
- Баллы начисляются только пока идёт сезон: до 1 октября 00:00 и после конца года не начисляются.

## API

`POST /api/season` (через `authorize`, как остальные ручки). Ответ:

```
{ now, season: { id, title, state: 'before'|'active'|'ended',
                 startsAt, endsAt, day, days },
  year:   { startsAt, endsAt },
  me:     { total, seasonPoints, rank },
  quests: [ { id, title, progress, goal, done, points } ],
  board:  [ { name, points, isMe } ],             // топ-10 по общей сумме
  champions: [ { seasonId, title, name } ] }      // считается на лету
```

- `state = before` до первого сезона: `season` — ближайший будущий, `quests` пуст.
- Таблица и место сортируются по `points DESC, MAX(at) ASC`: при равных баллах выше тот, кто набрал их раньше.
- `champions` считается на лету: для закончившегося сезона игрок с наибольшей суммой `points` этого сезона, `banned = 0`. Отдельной таблицы нет. Первый чемпион появится 1 января.
- `banned = 1` исключён из таблицы, места и призового списка, а также из таблиц по сложностям и места в них (`getBoard` и `getRank` фильтруют по `players.banned`).
- В таблице нет `tg_id`, своя строка помечена `isMe`.
- `now` отдаётся, чтобы клиент считал таймер по времени сервера, а не телефона.

Визит пишется в `handleSession` (открытие игры) и в `/api/season`, потому что Mini App, оставленное в фоне, может не вызывать `session()` целый день: `INSERT OR IGNORE INTO visits`, день по Москве.

## /metrics и админ-команды

Только когда одновременно `chat.type === 'private'` и `from.id` входит в `ADMIN_IDS`; иначе бот молча отвечает 200. `ADMIN_IDS` и `CHAT_SIZE` лежат в `[vars]` в `wrangler.toml` и объявлены в `Env`. Id Виктора — `956875`, подтверждён записью игрока «Виктор Сорваль, sorval» в боевой базе. Подлинность `from.id` обеспечивает секретный заголовок вебхука. Аргумент `/ban` разбирается как целое число.

`/metrics` считает (день по Москве):
- **DAU** = игроки с визитом сегодня; **WAU** за 7 дней; **MAU** за 30 дней; **липкость** = DAU / MAU. «Из N» берётся из `CHAT_SIZE` (переменная, сейчас 70).
- **Удержание D1, D7, D30:** объединённая когорта: игроки, чей первый день `f` попадает в `[сегодня-30, сегодня-N]`; удержан тот, у кого есть визит в день `f+N`. Ежедневные когорты при 70 игроках слишком малы. Если игроков в когорте нет, показывается «—». Данные D7 появятся не раньше 8 октября, D30 не раньше 31 октября.
- **Воронка (всего):** открыли игру → сыграли (есть принятый заплыв) → 1-й лагерь (`meters ≥ 400`) → 4-й лагерь (`meters ≥ 1900`) → финиш (пока «—»).
- **Заплывов на игрока в день** за 7 дней.
- **Задания:** доля выполненных среди активных на этой неделе; баллы за неделю.
- **Отклонено заплывов** за 7 дней, в процентах.
- Только числа, без имён.

`/season`: топ-10 общей таблицы с именами, `@username` и баллами, для ручной проверки призёров. Членство в чате игра больше не проверяет, так что «свой ли это человек» проверяется руками по `@username`. `/ban <id>` и `/unban <id>`: ставит и снимает `banned`; забаненный не попадает в таблицы (рейтинг сложностей и сезонную) и в призовой список.

## Проверка

- Юнит-тесты воркера: состояние сезона до, во время и после; номер недели и выбор трёх заданий; идемпотентность начисления при повторной отправке; баллы не начисляются вне сезона; правдоподобие `stats`; визиты не дублируются; расчёт DAU, WAU, MAU, удержания и воронки на подготовленных данных; закрытость `/metrics` и `/season` для не-админов; `banned` исчезает из таблиц.
- Клиент: чистая функция форматирования таймера проверяется тестом; вид карточки и экрана проверяется вручную (Chrome).
- Полный прогон `npx vitest run` перед выкладкой.
